## Features

- **Crafty (preview): ask about what you've selected, in any app** — Crafty is a helper for your whole Mac. Select something in any app and double-tap the left ⌘ key, or press ⌃⌥Space: a pie of actions opens at your pointer, and its middle names the action you point at. **Ask**, **Summarize**, **Explain** and **Reply** open a small panel that streams the answer from a Craft session, with **Insert at cursor** to put it where you were typing. **Rewrite** (improve, shorten, make friendlier or more formal, fix spelling) and **Translate** show a preview, and ↵ puts the result in place of your selection. **Send to** hands what you selected to a session, and **Screenshot** captures a region of the screen. Questions go to a new session labelled `crafty`, or to the session you chose with **Send Crafty Here** in its menu. When you call Crafty from a browser, it also passes on the page's address (macOS asks once per browser). Crafty is off by default: turn it on in Settings → App → Crafty (preview), where you can also choose the key to double-tap (⌘, ⌥ or ⌃) and whether it opens the pie or the panel. It needs Accessibility access: switching Crafty on asks for it, the double-tap starts a few seconds after you allow it, and until then the middle of the pie offers to open the setting. If Craft Agents is already on in the Accessibility list but Crafty still can't read your selection, the entry may be left from an older build, and Settings → App → Crafty explains how to renew it. Screen Recording is only needed for screenshots. The double-tap detection sees only modifier keys, never what you type. When an app doesn't share the selection, Crafty copies it with ⌘C and then restores your clipboard, so a clipboard manager may still record it. macOS only.

## Improvements

- **Agents can hand coding work to a session in its own worktree** — When an agent starts another session, it can now choose whether that session runs in Coding mode. Before, the new session always took the mode of the session that started it, so a regular session couldn't start a Coding one. The agent can also start the session in an existing git worktree, for example one it has just created for a new branch: the session then opens in Coding mode in that folder, the same setup as **Create new worktree** in the Coding chip. A folder that isn't a git worktree or checkout is refused, with a hint on how to create one. Partially addresses [#1120](https://github.com/craft-ai-agents/craft-agents-oss/issues/1120): tasks can't start in Coding mode yet.

## Bug Fixes

- **Pi sessions see images again** — In the packaged app, sessions on Pi connections replaced every image, however small, with "[Image omitted: could not be resized below the inline image size limit.]". That covered pasted images and screenshots, image files the agent read, and images in tool results such as browser or MCP screenshots. Since at least v0.11.1, the app had shipped without a file Pi needs to resize images. It's now included. Fixes [#1146](https://github.com/craft-ai-agents/craft-agents-oss/issues/1146) and [#979](https://github.com/craft-ai-agents/craft-agents-oss/issues/979).

- **Pi sessions no longer run code from the project folder when they handle an image** — To resize an image, a Pi session started a helper script that it looked up in the session's working folder instead of in the app. A project containing a file at that path had it run whenever an image was processed, in every permission mode, Explore included. The helper now always comes from the app.

- **Messages that arrive together no longer run two turns at once** — When two messages reached an idle session at nearly the same moment (for example two agents replying to the same session), both could start a turn, and the first one was cut off. The second message now waits behind the first, as it does while the agent is working. Queued messages also keep their place when a new message arrives just as a turn ends, and messages still queued when the app closed now run before one sent after it reopens.

- **A message sent as a Pi turn starts is no longer lost** — On connections that steer new messages into the running turn (Pi connections by default), a message sent in the first moments of a turn was shown as delivered, but the agent never received it. It's now queued and runs once the current turn ends.

- **A session no longer stays busy when its turn fails to start** — When setting up a turn failed (refreshing a source's sign-in, starting the agent or its source servers, or writing the summary for a session continued in a new one), the window showed the error but the session kept working, and messages sent afterwards were queued and never ran. The error now ends the turn, and the queued messages run.

- **Messaging another session no longer waits for its whole turn** — When an agent sent a message to an idle session, its own turn was blocked until that session had finished its entire turn, which could take minutes. A coordinating session looked stuck while its workers ran. The message now returns as soon as the other session has it, and says whether that session started a turn for it, took it into the turn it was running, or queued it; any answer still arrives later as a message. Fixes [#1132](https://github.com/craft-ai-agents/craft-agents-oss/issues/1132).

- **Allow and Deny taps in Telegram work while the agent waits** — Tapping Allow on a permission prompt in Telegram was ignored, and the session kept waiting until you approved it in the app. The bot handles chat updates one at a time and, after each message, waited for the whole turn, so the tap was only read once the turn was over, and by then the prompt had been cleared as stale. `/stop`, `/bind` and plan acceptance from the chat were held up the same way, so you couldn't switch sessions from the chat while a turn ran. Messages from the chat now hand off to the session right away, so taps and commands are handled immediately, and a prompt is only cleared once it's answered (in the chat, the app or the WebUI) or the turn ends. A prompt answered in one app window now also disappears from the others. Fixes [#1130](https://github.com/craft-ai-agents/craft-agents-oss/issues/1130) and [#793](https://github.com/craft-ai-agents/craft-agents-oss/issues/793).

- **Lark messages are confirmed right away** — Lark sends a message again when the bot hasn't confirmed it within 3 seconds, and Craft confirmed a message only after the agent had answered it. Every answer that took longer was processed again, so one question got two to four replies. Craft now confirms a message as soon as the session has it. A message that Lark sends again for another reason is still answered again. Related to [#1125](https://github.com/craft-ai-agents/craft-agents-oss/issues/1125).

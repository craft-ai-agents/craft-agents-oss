# 平台报价查找

本 skill 负责采购业务层的平台结果整理。这里按采购需要处理采集层返回的结构化证据。

## 工作流

1. 确认入口：本地库存已经查完为空，或用户明确要求继续查外部平台。
2. 保留用户原始型号：不要先合并后缀、包装、温度等级或版本号。
3. 首轮必须直接平台全覆盖：准确度优先，调用 `scrape-engine` 的 `engine.py --source-set direct`，一次性跑当前可用的全部直接库存/报价平台；不要手工截取 `source_catalog.yaml` 或自己挑“核心平台”。
4. 首轮不要跑聚合平台或替代候选源：聚合平台会重复覆盖多个真实平台，替代候选源不是普通库存报价平台；二者都不能算首轮直接平台覆盖。
5. 展示搜索覆盖：每次输出都先列出本次实际查询的网站/source 覆盖。首轮列 `--source-set direct` 展开的直接平台；二轮列聚合平台（如有）；没有跑聚合平台就写“二轮聚合：未使用，待用户确认”。覆盖清单必须来自本次实际传入的 source-set/source 和返回的 rows/errors，不能凭印象补。
6. 核对首轮覆盖状态：每个直接平台都必须落到一种状态：有结果、正常无匹配、本次未取到、访问受限、维护/连接问题。只有每个直接平台都有状态，才能写“首轮直接平台已覆盖完成”；若有平台状态缺失，写“仍有平台状态未确认”，不要写全平台完成。
7. 首轮完成后先汇报直接平台结果，并把聚合平台放到下一步提问：是否继续用 `--source-set aggregator` 做二轮补充或交叉验证。用户确认后再跑聚合平台。替代候选源只在任务转为替代料判断时使用，不混入普通平台报价结果。
8. 取得结构化平台证据：只消费返回的型号、平台、品牌、描述、库存、价格、MOQ、交期、链接和错误状态。
9. 做型号一致性核对：平台返回型号与用户型号不完全一致时，逐字符写清差异，例如多了包装后缀、少了温度等级、版本字母不同。
10. 合并同一平台的重复行：同平台同型号保留库存/价格最完整的行，证据链接不同但信息互补时可以合并到同一行。
11. 区分状态：有结果、正常无匹配、本次未取到要分开写；访问受限或报错只能说本次未取到，不能说成无货。

## 输出

输出给采购看平台证据，不输出采集过程。没有上层指定格式时，用下面的结构：

```text
平台总览表（首轮直接平台 N 个；二轮聚合：未使用，待用户确认）

| 平台 | 状态 | 返回型号 | 库存 | 最低价/MOQ | 交期 | 证据 | 备注 |
|---|---|---|---|---|---|---|---|
| digikey | 有库存 | LM358DR2G | 34,261 pcs | $0.24 @1 | 未返回 | 产品页 | 完全一致 |
| ickey | 有库存 | LM358A-SR | 16,000 pcs | ¥0.42 @750 | 5-10 工作日 | 来源字段无链接 | 差异：多后缀 A |
| avnet | 有报价/可订 | LM358DR2G | 未返回 | $0.21 @2500 | 未返回 | 搜索页 | MOQ 2500 |
| tme | 无匹配 | - | - | - | - | 搜索页 | 正常无匹配 |
| rs-uk | 本次未取到 | - | - | - | - | 搜索页 | 反爬拦截 |
| newark | 本次未取到 | - | - | - | - | - | 缺 API key |

平台状态汇总：有库存 X / 有报价或可订 X / 已知无库存 X / 无匹配 X / 本次未取到 X。

详细结果（仅展开有库存、有报价或需要人工确认的平台）

digikey
- 返回型号：LM358DR2G；型号一致性：完全一致
- 品牌/描述：onsemi / IC OPAMP GP 2 CIRCUIT 8SOIC
- 库存：34,261 pcs
- 价格/MOQ：$0.24 @1 起
- 交期：未返回
- 证据：https://www.digikey.com/en/products/detail/onsemi/LM358DR2G/661123
- 需确认：无

ickey
- 返回型号：LM358A-SR；型号一致性：差异：你查的是 LM358，返回 LM358A-SR，多了后缀 A
- 品牌/描述：3PEAK/苏州思瑞浦微电子 / SOP-8
- 库存：16,000 pcs
- 价格/MOQ：¥0.42 @750 起
- 交期：5-10 工作日
- 证据：来源字段无链接
- 需确认：后缀 A 是否可接受

未展开平台说明：
- 无匹配：<平台列表>
- 本次未取到：<平台：原因>

```

写法要求：

- **先表格后明细**：进入外部平台结果后，第一屏必须先显示 `平台总览表`；不要先写型号科普、推荐顺序或长篇说明。
- 每个 `--source-set direct` 平台必须一行。表格平台数必须等于 `--list-source-set direct` 展开的平台数；缺平台就写“仍有平台状态未确认”。
- 表格状态只用这五类：`有库存`、`有报价/可订`、`已知无库存`、`无匹配`、`本次未取到`。
- 同一平台多行结果时，表格只保留最能代表平台情况的一行；其他型号或阶梯价放到详细结果。
- 状态归类优先级：有库存 > 有报价/可订 > 已知无库存 > 无匹配 > 本次未取到。
- 不出现采集过程、技术实现、JSON 字段
- `有库存` 行带核心摘要：库存量 + 返回型号 + 最低价/MOQ
- `无匹配` 行可只写平台状态和证据，不解释成“无货”
- 部分平台返回的是原始页面文本（`note` 字段）。读到 `note` 有内容时，用简单的文本匹配提取可用信息（搜到几条结果、价格行、库存数字）；提取出来的结果归入 `有库存`，但注明"基于页面文本提取，需复核"。提取不出有效数据或 `note` 为空的平台归入 `无匹配`
- `本次未取到` 写具体原因（反爬拦截/未响应/维护/缺 API key），不写"无货"
- 详细结果中 `返回型号` 后加一致性标注：`✓ 完全一致` / `⚠ 差异：逐字符说明`
- `库存` 写数字 + pcs；`0` 写"已知无库存"，空写"未返回"
- `价格` 取最低阶梯价注明起订量；无阶梯价写"未返回"
- `交期` 有则写原文，无则写"未返回"
- `证据` 优先给产品页链接；没有链接写"来源字段无链接"
- `需确认` 写需要采购人工核实的点；没有写"无"
- 不做采购推荐排序；只呈现平台事实和需确认点。

## 反合理化表格

| 常见借口 | 反驳 |
|---|---|
| “聚合平台覆盖了很多平台，首轮一起跑更全面。” | 首轮要确认每个直接平台的真实状态；聚合平台只能二轮补缺或交叉验证，不能替代直接平台覆盖。 |
| “我已经查了 DigiKey/Mouser/几个常见平台，可以先总结。” | 首轮是 `--source-set direct` 展开的全量直接平台，不是常见平台抽样；跑不完就写未完成，不要总结成全平台。 |
| “有结果的平台很多，先把有货渠道详细写完。” | 先给全平台总览表，让采购快速看到哪些平台有货、无匹配或本次未取到；详细结果放在表格后。 |
| “首轮跑了一批平台，就可以说全平台完成。” | 只有全部直接库存/报价平台都有状态，才能说首轮直接平台已覆盖完成；缺状态就必须写未确认。 |
| “平台没返回结果，就是无货。” | 正常无匹配和本次未取到要分开；访问受限不是无货证据。 |
| “型号差一个后缀也算同一个。” | 后缀可能代表包装、温度、速度、版本或封装，必须逐字符说明差异。 |
| “看到价格最低的一行，直接推荐给采购。” | 本 skill 只汇总平台证据；不做供应商准入、下单建议或性价比排序。 |
| “WebSearch 看到库存页，也能报库存价格。” | 库存、价格、可得性只认结构化平台证据；网页搜索只能辅助识别型号信息。 |
| “平台返回 similar/alternate，就能当替代料。” | 平台相似项只是线索，不能在这里下可替代结论。 |

# 批量找料 · 多 agent 编排

用户一次给**多个型号**(粘贴一张表 / 列了一串料 / "这一批帮我都查下")时,别一个一个串着查——给每个型号起一个**子会话**并行跑标准找料流程,各子会话把结论回传你(父会话),你攒齐后汇总成一张对比给采购。

> **只在多型号时用。** 单个型号走顶部标准找料流程,别 spawn。同一个型号内部"平台 vs 供应商"那种并行是单会话内的并行,也不在这里。

## 编排步骤

### 1. 先拿自己的 sessionId
调 `get_session_info`(不带参数 = 当前会话)拿到你的 `sessionId`,记作 `<父ID>`——子会话要靠它回传。

### 2. 每个型号 spawn 一个子会话
对每个型号 `X` 调 `spawn_session`:
- `prompt` 圈定型号 + 要求干完回传,例如:
  > 你是一次批量找料里的一个子任务,**只负责型号 `X`**。按标准找料流程查(先本地库存,再按需查平台/分销),得出库存 / 价格 / 供应商 / 货期,或"无货"的明确结论。**完成后用 `send_agent_message` 把结论发回 session `<父ID>`,一条消息讲清这个型号:有无货、哪家、价格、货期、关键提示;别附查询过程、别啰嗦。**
- `name` 用 `找料-X`、`labels` 用 `["批量找料"]`,方便后面 `list_sessions` 过滤。
- 连接 / 模型 / 权限都省略,继承工作区默认(子会话自带本工作区的技能和总则,会自己按标准流程查,你不用在 prompt 里重教流程)。

### 3. 并发卡小(prod 资源有限)
**一次最多并行 5 个子会话**。每个子会话各自要跑采集引擎 / 浏览器,生产机只有 4C4G,开太多会拖垮。型号超过 5 个就**分批滚动**:先 spawn 前 5 个,之后每收到一个回传、就补 spawn 下一个,始终保持约 5 个在跑。

### 4. spawn 完就结束这一轮,等回传
子会话是**异步**跑的。spawn 完当前批次后**结束你这一轮**,等它们回传——每条 `send_agent_message` 会重新唤醒你。**不要在一轮里空轮询硬等。**

### 5. 攒齐 → 汇总
你会被各子会话的回传逐条唤醒(每条带 sender 信封 `[Message from session … (找料-X)]`,据子会话名 `找料-X` 就能对上是哪个型号)。**记牢你在等哪几个型号、已经收到哪几个。** 每次被唤醒:
1. 收下这条结论,标记该型号已回。
2. 还有没 spawn 的型号,补 spawn 下一个(保持并发 ~5)。
3. **N 个全回齐了**,才把所有结论**汇总成一张对比**给采购(每行一个型号:有无货 / 哪家 / 价格 / 货期 / 提示)。别每回来一条就零散地丢给采购。

### 6. 掉线兜底
某个子会话迟迟不回(明显超时),用 `list_sessions`(按 label `批量找料` 过滤)或 `get_session_info` 看它状态。汇总时把"还没出结果 / 失败"的型号**如实列出**,别干等到死,也别假装查过。

## 反合理化表

| 常见借口 | 反驳 |
|---|---|
| “型号不算多，我串行查完更省事。” | 多型号任务用子会话并行；父会话负责拆分、收口和汇总。 |
| “一次把所有型号都 spawn 出去最快。” | 生产资源有限，最多并行 5 个，超过就滚动补位。 |
| “回一个型号就先发一个结果给采购。” | 攒齐后再汇总成一张对比；中间结果只用于记录状态。 |
| “子会话很久没回，我就编个无货。” | 用会话状态兜底；失败或未完成要如实列出。 |

## 边界
- **父会话只编排,不自己查料**:负责拆分型号、滚动 spawn、收口、汇总;实际查料都在子会话里。
- 一条 `send_agent_message` 回传 = 一个型号的最终结论,不是中间过程。
- 汇总给采购时用业务语言、一张对比表;子会话里的技术细节别外漏(同总则)。

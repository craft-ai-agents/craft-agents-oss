# 批量任务 · 多 agent 编排

用户一次给**多个项目**(型号、品牌、品类都算)、且要做的是**同一种任务**时,别一个一个串着处理——给每个项目起一个**子会话**并行跑,各子会话把结论回传你(父会话),你收齐后汇总成一张对比给采购。

> **只在"多项目 + 单一任务类型"时用。** 单个项目走对应的标准业务 skill,别 spawn。同一批里如果既要找料又要查供应商,那是两种任务,分两批分别编排,不要塞进一次 spawn 里。
> **完整度要求。** 子会话的处理效果必须和该任务单项处理时同等完整——不能因为是批量任务就抄近路、少查几步。具体某个任务类型"同等完整"是什么标准,由父会话按平时用那个业务 skill 时的判断力来定,不在本 skill 里重复。

**本 skill 只管编排机制,不认识具体任务类型。** 判断"这批要做什么、该用哪个业务 skill"是父会话自己的活,跟平时单个项目时选 skill 的判断力一样——本 skill 不穷举、不代替这个判断。

## 编排步骤

### 1. 先拿自己的 sessionId
调 `get_session_info`(不带参数 = 当前会话)拿到你的 `sessionId`,记作 `<父ID>`——子会话要靠它回传。

### 2. 用 larkdepot 落地批量结果
父会话生成一个批次 ID(如 `proc-20260702-001`)。批量结果的落地和读回走 `larkdepot`(见该 skill 的"批量任务结果写回"配方),不要另建 JSONL 文件,也不要发明别的存储方式——具体命令语法在 `larkdepot` 里,本 skill 不重复。

子会话完成后先用 `larkdepot` 把完整细节落一行本地(批次 ID + 项目标识 + 结果状态 + 打包成 JSON 的细节),再用 `send_agent_message` 回传**短状态**给父会话;不要把完整结果粘到回传消息里。父会话最终汇总时从 `larkdepot` 读回这批的全部行。

### 3. 每个项目 spawn 一个子会话
对每个项目 `X` 调 `spawn_session`:
- `prompt` 先判断**这批任务该用哪个业务 skill**(比如全是找料就是标准找料流程,全是找替代料就是 `procurement-alternative-search`,全是查供应商就是 `procurement-supplier-shortlist`,以此类推),再圈定项目 + 要求干完回传,例如:
  > 你是一次批量任务里的一个子任务,**只负责项目 `X`**。按 `<对应业务 skill>` 的标准流程处理,处理效果必须和单项处理时同等完整,不能因为是批量任务就抄近路。完成后先用 `larkdepot` 把完整细节落一行本地(批次 ID `<批次ID>`、项目标识 `X`、结果状态、细节打包进结果 JSON 字段);**然后用 `send_agent_message` 把短状态发回 session `<父ID>`:项目标识、完成/未完成、结果摘要、批次 ID;不要把完整结果粘到回传消息里。**
- `name` 用 `批量-X`、`labels` 用 `["批量任务"]`,方便后面 `list_sessions` 过滤。
- 连接 / 模型 / 权限都省略,继承工作区默认(子会话自带本工作区的技能和总则,会自己按 `<对应业务 skill>` 的标准流程处理,你不用在 prompt 里重教那个 skill 的具体做法)。

具体某种任务(比如找料)对"同等完整"的量化要求、超时怎么处理,如果需要写成固定配方供以后复用,放进 `references/`,不要写回本节——本节只讲编排机制本身。当前已有的配方:[references/scenario-part-finding.md](references/scenario-part-finding.md)(批量找料场景)。

### 4. 并发上限（生产机资源有限）
**默认最多并行 5 个子会话**。项目超过 5 个就**分批滚动**:先 spawn 前 5 个,之后每收到一个回传、就补 spawn 下一个,始终保持当前并发上限。

只有已经观测到命令超时或资源压力,例如多个子会话同时跑重活出现 shell/agent 工具超时、浏览器崩溃或明显排队,才再临时收缩到 2-3 个活跃子会话。收缩并发是保护完整度的恢复动作,不是默认规则。

### 5. spawn 完就结束这一轮,等回传
子会话是**异步**跑的。spawn 完当前批次后**结束你这一轮**,等它们回传——每条 `send_agent_message` 会重新唤醒你。**不要在一轮里空轮询硬等。**

### 6. 收齐 → 汇总
你会被各子会话的回传逐条唤醒(每条带 sender 信封 `[Message from session … (批量-X)]`,据子会话名 `批量-X` 就能对上是哪个项目)。**记牢你在等哪几个项目、已经收到哪几个。** 每次被唤醒:
1. 收下短状态,用 `larkdepot` 读回这个批次的记录,检查是否已有该项目那一行;没有落行就让子会话补写,不要把长结果塞回对话。
2. 还有没 spawn 的项目,补 spawn 下一个(保持当前并发上限)。
3. **全部回齐了**,父会话最终汇总从 `larkdepot` 读取,再给采购一张简短对比表(每行一个项目,列名按这批的任务类型定,比如找料是"有无货/哪家/价格/货期",查供应商是"候选家数/类型/联系方式")。别每回来一条就零散地丢给采购。

### 7. 超时处理
某个子会话迟迟不回(明显超时),用 `list_sessions`(按 label `批量任务` 过滤)或 `get_session_info` 看它状态。汇总时把"还没出结果 / 失败"的项目**如实列出**,不要空等,也别假装处理过。

## 边界
- **父会话只编排,不自己处理业务**:负责判断任务类型、拆分项目、滚动 spawn、收口、汇总;实际处理都在子会话里,按子会话被指派的那个业务 skill 走。
- 一条 `send_agent_message` 回传 = 一个项目的短状态,不是详细结果;详细结果以 `larkdepot` 落的行为准。
- 汇总给采购时用业务语言、一张对比表;子会话里的技术细节别外漏(同总则)。
- 一批只处理一种任务类型。混合任务类型的需求,拆成多批分别编排,不要在一次 spawn 里塞两种业务 skill。

## Rationalization Table

| Excuse | Reality |
|---|---|
| “项目不算多，我串行处理完更省事。” | 多项目任务用子会话并行；父会话负责判断任务类型、拆分、收口和汇总。 |
| “一次把所有项目都 spawn 出去最快。” | 默认最多并行 5 个子会话，超过就滚动补位；只有已经观测到命令超时或资源压力，才再临时收缩到 2-3 个。 |
| “批量任务随便简化一下流程就够了。” | 子会话处理效果必须和单项处理时同等完整；具体标准照该任务类型平时的业务 skill 判断力来定，不因为是批量任务就抄近路。 |
| “这批型号里有几个其实想查供应商，顺手一起 spawn 了。” | 一批只处理一种任务类型；混合任务拆成多批分别编排。 |
| “回一个项目就先发一个结果给采购。” | 收齐后再汇总成一张对比；中间结果只用于记录状态。 |
| “子会话把完整结果回传给父会话更方便。” | 子会话用 `larkdepot` 落完整细节；回传只发短状态和批次 ID。 |
| “子会话很久没回，我就编个结果。” | 用会话状态兜底；失败或未完成要如实列出。 |

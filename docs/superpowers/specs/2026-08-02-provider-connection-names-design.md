# Provider Connection Names

## Goal

Show the actual provider name for LLM connections instead of implementation-oriented labels such as `ARCHstudio Backend (API Key) 2`.

## Naming Rules

- API-key connections use the selected provider's display name, such as `Anthropic`, `OpenAI`, `Google AI Studio`, or `OpenRouter`.
- Duplicate connections keep the same provider-only display name; internal slugs remain unique.
- OAuth connections retain their product names: `Claude Max`, `ChatGPT Plus`, and `GitHub Copilot`.
- Unnamed custom endpoints derive a readable provider name from their hostname, such as `apihub.agnes-ai.com` to `Agnes AI`.
- Unknown provider keys fall back to the existing generic name rather than producing an empty label.

## Existing Connections

Startup migration updates names only when they match an autogenerated `ARCHstudio Backend (...)` pattern. User-renamed connections remain unchanged.

## Implementation

Shared naming helpers are the source of truth for provider and endpoint display names. Connection setup uses the selected provider name for presets and a hostname-derived name for unnamed custom endpoints. Storage migration uses the same recognition rules for legacy autogenerated names.

## Error Handling

If provider metadata is unavailable, connection creation retains the current generic fallback. Naming must never prevent provider setup or authentication.

## Testing

- Provider API-key connections receive real provider names.
- Duplicate slugs keep provider-only display names.
- OAuth and explicitly named custom endpoints are unchanged.
- Unnamed custom endpoints derive readable hostname-based names.
- Legacy autogenerated names migrate.
- User-defined names are preserved.

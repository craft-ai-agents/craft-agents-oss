# 项目专属 writing-skills fork 设计

## 问题

写/改 skill 时,repo 里已有几十个 skill 长期各写各的,常见问题(输出格式不统一、要不要拆新 skill、要不要写一条新约束)没有一个稳定的判断依据,全靠临场感觉,容易越堆越乱。

已有的 `superpowers:writing-skills`(插件自带,全局)是一套成熟的 TDD 式写 skill 方法论,覆盖了大部分"怎么写 SKILL.md 这份文档"的判断,但有三处空白/水土不服:

1. 没有回答"skill 执行完,产出的内容该长什么形状"——它管文档怎么写,不管文档执行后的输出契约。
2. "要不要拆成新 skill"的边界判断是针对它自己的语境("Claude 个人可复用技巧库")写的,换成"某个目录下的 skill 会被整体镜像/部署给最终用户使用"这种场景,判断标准需要一个不同的版本。
3. 它已经讲了"不要为假设场景加内容",但没有讲透一个更细的坑:**哪怕是真实观察到的失败,写成规则时也必须先剥掉具体案例、只留泛化方法论**——具体案例焊进规则,以后会被误当成标准答案抄。

## 决策

Fork `superpowers:writing-skills` 到本仓库 `.claude/skills/writing-skills/`,作为项目技能。**名字保持 `writing-skills` 不变**——Skill 工具按目录就近原则解析,项目目录下的同名 skill 会覆盖全局插件版本,在本仓库工作时自动生效,不需要改名或额外配置。

完整复制原版所有文件(`SKILL.md`、`anthropic-best-practices.md`、`persuasion-principles.md`、`testing-skills-with-subagents.md`、`graphviz-conventions.dot`、`render-graphs.js`、`examples/`),保证 fork 后独立于插件版本变化,不依赖外部更新。

在 fork 出来的 `SKILL.md` 正文追加三段内容,**全部使用通用词汇表达,不引用任何具体业务场景、项目名称或领域案例**:

1. **输出形状测试**:skill 执行后的产出,按数据形状分类挑格式——多条记录各自一个状态 → 列表/表格;单一主体多个属性 → 属性表;两个对象逐项比较 → 对比表;单一判断+证据+缺口 → 结论优先的分段格式。不预先规定具体列名或词汇,由数据形状决定用哪种骨架。
2. **部署边界测试**(细化原版"When to Create a Skill"):当某个目录下的 skill 会被整体镜像/部署为面向最终用户的产品能力时,拆分新 skill 的判断标准改为三因子测试——触发语义、所需工具链、产出物三者只要有一个不同,就该拆成独立 skill;仅是同一任务的不同变体,用一个 skill + 参考文件分层即可。这类会被部署的 skill 之间可以在正文里点名区分边界,但不能写"先执行另一个 skill"这种指挥语气——路由决策应该留在更上层的入口配置,不要让 skill 之间产生强制执行顺序的耦合。
3. **不焊死具体案例**(补充原版 Iron Law 的推论):即使一条规则来自真实观察到的失败,写进 skill 正文时也只能保留**泛化后的方法论**,具体案例(实例名称、具体输入输出、测试数据)一律不进正文——留在写这条规则时参考的诊断记录/测试记录里。规则本身要能脱离产生它的那一次具体事件、独立成立。

## 非目标

- 不建任何包含具体业务场景的示例文件。三段新增内容需要例子时,使用与原版风格一致的中性技术类比,不引入任何领域词汇。
- 不在这份设计里处理"用这个 skill 去改具体哪些业务 skill 的输出格式"——那是这个元 skill 建成后的下一步应用工作,不属于本次范围。

## 验收

- `.claude/skills/writing-skills/SKILL.md` 存在,包含原版全部内容 + 三段新增内容。
- 三段新增内容读一遍,不出现任何业务名词、项目路径名、领域型号/案例。
- 在本仓库内调用 `Skill writing-skills` 时加载的是这份 fork,而不是插件全局版本(按目录就近规则应自动成立,写计划阶段验证)。

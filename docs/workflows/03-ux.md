# Workflow UX spec

This doc describes the surfaces a user touches. Read [`02-runtime.md`](./02-runtime.md) for what's happening underneath.

## Sidebar placement

Add a top-level **Workflows** entry, parallel to **Chat** and **Agents** in the sidebar. Why top-level (not under **Library** with Tools/Skills/Workspace Context):

- Workflows are *executable*, like agents — they're nouns the user runs, not reference material.
- The **Run page** is one of the most-visited views once people start using workflows. Burying it under Library hides it.

Final sidebar shape after this lands:

```
Chat
Agents
  ├ Orchestrator (pinned)
  ├ <activated agents>
  ├ Manage agents
  └ Past
Workflows                    ← NEW
  ├ <activated workflows>
  ├ Manage workflows
  └ Recent runs              ← NEW (chronological run history)
Library
  ├ Tools
  ├ Skills
  └ Workspace Context
Automations
Settings
```

## Page-level surfaces

| Surface | Route | Purpose |
|---------|-------|---------|
| Workflows list | `/workflows` | Browse, activate, create, delete. Pattern-mirror the Agents list. |
| Workflow detail | `/workflows/<slug>` | Read-only summary + Run button + edit + recent runs. |
| Workflow editor | `/workflows/<slug>/edit` | YAML+markdown editor, like AGENT.md edit. Live validation. |
| Run input form | (modal off detail page) | Fill in `trigger.inputs`, click Run. |
| **Run page** | `/runs/<runId>` | The killer view. See below. |
| Recent runs | `/workflows/runs` | Cross-workflow run history. |

## The Run page (the killer view)

A vertical pipeline of cards, one per step, plus a header with run-level info and a **side pane** that opens when you click a card.

### Layout sketch

```
┌─ Weekly Content Pipeline ────────────────────── ▶ Cancel ⟳ Rerun ⊕ Fork ─┐
│  Run id 8c3a · started 9:01am · 4m elapsed · 12.4k tokens                │
├──────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│  🟢 1. Research          @researcher   12s · 2.1k tokens                 │
│      Found 4 primary sources on retrieval-augmented generation...   ›    │
│                                                                          │
│  🟢 2. Draft             @writer       24s · 3.8k tokens                 │
│      Drew up a 600-word post structured around the three best sources... │
│                                                                          │
│  🟡 3. Critique          @critic       running...                        │
│      The opening paragraph buries the lede. Recommend pulling the...     │
│                                                                          │
│  ⚪ 4. Revise            @writer       queued                            │
│                                                                          │
│  ⏸ 5. Approve & publish  @publisher    awaiting human                   │
│      [ Approve ] [ Reject ] [ Edit prompt and continue ]                 │
│                                                                          │
└──────────────────────────────────────────────────────────────────────────┘
```

### Card states

| State | Icon | Notes |
|-------|------|-------|
| `queued` | ⚪ | Greyed, no body. |
| `running` | 🟡 (pulsing) | Partial output streams into the body as it generates. |
| `succeeded` | 🟢 | Output preview is the first 1–2 sentences with a "›" affordance to expand. |
| `failed` | 🔴 | Body shows error code + message + a Retry button. |
| `skipped` | ⚪ (dashed) | Body shows the `when:` condition that evaluated falsy. |
| `awaiting-human` | ⏸ | Body shows step output + Approve/Reject/Edit buttons. |

### Side pane — drill-down

Clicking any card opens a right-side pane (≈40% viewport width) showing **the underlying session**. Reuse the existing session-viewer component verbatim — every step IS a real session.

In the side pane the user can:
- Read the full transcript.
- **Inject a message into a running step.** The runner doesn't advance until the session reports complete, so user nudges work mid-flight.
- Fork a new branch session from this step (creates a free-standing session, doesn't affect the run).
- Rerun this step alone (Phase 2 — restarts from this step downward).

Closing the side pane returns to the pipeline view. State is preserved.

### Run-level controls

Top-right of the header, in this order:

| Control | Phase | Behavior |
|---------|-------|----------|
| **Cancel** | 1 | Hard-aborts the active step's session, marks run cancelled. Confirmation modal if more than 30s into the run. |
| **Rerun** | 1 | Opens the input form pre-filled with the previous run's inputs. Creates a brand new run. |
| **Fork** | 2 | Saves a copy of the underlying `WORKFLOW.md` as `<slug>-fork`, opens in editor. Useful for "this was almost right, let me tweak it." |
| **Resume from step…** | 2 | Pick a step; runner reuses outputs from earlier steps, reruns from picked step downward. |

### Approval UI for `humanCheckpoint`

When a step has `humanCheckpoint: true` and reaches `awaiting-human`:

- Card shows the step output prominently.
- Three primary buttons: **Approve**, **Reject** (marks run as failed), **Edit prompt and continue** (opens the next step's prompt for one-time tweaks before it runs).
- Cross-platform notification fires when a run hits `awaiting-human` — users walk away from long workflows and come back to a notification badge on the dock/taskbar.

## Workflows list page

Same shape as the Agents list. Each row:

| Column | Notes |
|--------|-------|
| Avatar + name | Click → workflow detail. |
| Description | Truncated. |
| Trigger type | Badge: `manual` / `schedule` / `automation` / `webhook`. |
| Last run | Relative time + colored status dot. |
| Run | Inline button — opens input form. |
| ⋯ | Edit, duplicate, delete, export. |

Top-right: **+ New Workflow** button. Templates are seeded on first run (parallel to how Concierge/Orchestrator are auto-seeded), see [`05-examples.md`](./05-examples.md).

## Workflow editor

Single-file markdown editor. Pattern: copy the AGENT.md edit dialog (`apps/electron/src/renderer/components/app-shell/AgentEditDialog.tsx`).

Two modes, toggle in the header:

- **Form mode** — friendly form for `name`, `description`, `avatar`, `trigger`, plus an ordered list of step cards (drag to reorder, +/− to add/remove). Each card has fields: `id`, `agent` (combobox of activated agents), `input` (textarea with templating autocomplete), advanced (`outputSchema`, `timeout`, `retries`, `when`, `humanCheckpoint`).
- **Source mode** — raw `WORKFLOW.md` editor. Live validation; errors inline.

Both modes write the same file. Users who like ergonomic forms get them; power users edit raw and save.

### Templating autocomplete

In the `input` textarea, typing `{{` opens a popover listing:
- `trigger.<input>` for every declared trigger input
- `steps.<id>.output` for every step earlier than the current one
- (When that step has `outputSchema`) `steps.<id>.output.<field>` for every top-level field in its schema

This is not optional — without autocomplete users will fat-finger references and only learn at run time.

## Recent runs page

Cross-workflow chronological list. Filterable by workflow, state, date. Each row links to its Run page.

## What we are NOT building (yet)

- Drag-and-drop visual node graph (Phase 5+).
- Multi-user run ownership / sharing — local-first, single-user assumption.
- Run cost dashboards beyond per-run token totals.
- Workflow marketplace / discovery surface (later, when there's a community).

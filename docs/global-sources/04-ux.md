# Global Sources — UX

## Sources page: three tiers, one list

The existing Sources page lists workspace-defined sources. Extend to show a unified list
across all tiers, with a tier badge and tier-aware actions.

```
┌─ Sources ───────────────────────────────────────── [+ Add] [Browse Global ▾] ┐
│                                                                              │
│  ┌─ Notion ─────── 🌐 global ──── ✓ activated ─── personal account ────────┐ │
│  │  Knowledge base + docs.                       [Use different creds]     │ │
│  │  Status: Connected.                           [Deactivate]              │ │
│  └────────────────────────────────────────────────────────────────────────┘ │
│  ┌─ Slack ──────── 🌐 global ──── ✓ activated ─── workspace creds (work) ─┐ │
│  │  Workspace messaging.                         [Revert to global]       │ │
│  │  Status: Connected.                           [Deactivate]             │ │
│  └────────────────────────────────────────────────────────────────────────┘ │
│  ┌─ project-data ─ 🏠 workspace ── ✓ enabled ─── needs auth ──────────────┐ │
│  │  Custom MCP server for project data.          [Promote to Global]      │ │
│  │  Status: Needs authentication.                [Edit] [Delete]          │ │
│  └────────────────────────────────────────────────────────────────────────┘ │
│  ┌─ Linear ─────── 🌐 global ──── ○ dormant ─────────────────────────────┐ │
│  │  Issue tracker. Activate to use in this workspace.                    │ │
│  │                                               [Activate]              │ │
│  └────────────────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────────────────┘
```

Tier badges:
- 🏠 **workspace** — defined in `<workspace>/sources/<slug>/`
- 🌐 **global** — defined in `~/.agents/sources/<slug>/`, activated in this workspace
- 🌐 **dormant** — defined globally, not activated here (renderable when "Show dormant" toggle is on)
- 📁 **project** — existing project-tier source (no UX change)

## Per-row actions

Action visibility is tier-aware:

| Action | Workspace | Global (active) | Global (dormant) |
|---|---|---|---|
| Edit config | yes | no — read-only | no |
| Delete | yes | no — global library is read-only from workspace UI | no |
| Promote to Global | **yes** (when no global exists with same slug) | n/a | n/a |
| Activate in this workspace | n/a | n/a | **yes** |
| Deactivate from this workspace | n/a | **yes** | n/a |
| Use different creds in this workspace | n/a | **yes** (when not already overridden) | n/a |
| Revert to global creds | n/a | **yes** (when overridden) | n/a |
| Manage global definition | n/a | opens a global-tier detail page | opens detail (read-only preview) |

The global library itself is managed from a separate page: **Settings → Global Sources
Library** (or similar). That page has the create/edit/delete actions for global sources.
Workspaces only activate / deactivate / override.

## Workflows

### Activate a dormant global

1. User clicks the source row (or the "Activate" button if rendered).
2. Modal:
   ```
   Activate "Notion" in this workspace?
   This source uses global credentials (personal account).
   [Cancel] [Activate]
   ```
3. On confirm: RPC writes slug into `.global-sources.json`. UI updates atom. If a session
   is open, the source is hot-loaded into running agents (existing reload pipeline).

### Use different credentials in this workspace

1. User clicks "Use different creds in this workspace" on an active global source.
2. Modal:
   ```
   Override credentials for "Slack" in this workspace?
   The global credentials will not be touched. This workspace will not have access
   until you log in below.
   [Cancel] [Override and Log In]
   ```
3. On confirm: RPC writes a workspace credential record `{ override: true, value: null }`,
   then opens the source's auth flow (OAuth, paste-bearer-token, etc.).
4. Auth completes → workspace credential record updated with the new value. Source becomes
   usable in this workspace. Other workspaces unaffected.

### Revert to global creds

1. User clicks "Revert to global creds" on an overridden source.
2. Modal:
   ```
   Delete workspace-specific credentials for "Slack"?
   This workspace will revert to using the global credentials.
   [Cancel] [Delete Override]
   ```
3. On confirm: RPC deletes the workspace credential record. UI refetches; row re-renders
   showing global creds in use.

### Promote a workspace source to global

1. User clicks "Promote to Global" on a workspace source.
2. Modal:
   ```
   Promote "project-data" to your global library?
   ☐ Also copy the credentials currently set in this workspace
       Recommended OFF — log in fresh at the global tier instead.

   Once promoted, the source becomes available to activate in any workspace.
   The workspace copy stays in place and continues to override the global with
   the same slug; you can delete it later if you want.

   [Cancel] [Promote]
   ```
3. On confirm: RPC `mirrorSourceToGlobal(ws, slug, { includeCredentials })`.
4. On success: toast confirmation, source now visible at the global tier.

### Browse and add from global library

1. User clicks "Browse Global ▾" → opens a panel listing all global sources with their
   current activation state in this workspace.
2. Each row has an Activate / Deactivate toggle.
3. Search + filter by tag.
4. From this panel, "+ New Global Source" links to the Settings → Global Sources Library
   page where definitions are managed.

## Settings → Global Sources Library page

A new top-level settings page mirrors the existing Skills global library page (which exists
post the auto-mirror commit). Lists every global source with:

- Tier badge (global)
- Activation count: "Activated in 3 workspaces"
- Edit definition (config.json round-trip)
- Edit guide.md
- Manage credentials (the `__global__` set)
- Delete (warns if any workspace has it activated)

This page is reached through Settings, not through a workspace's Sources page. Editing
here is the *one* way to mutate a global source's definition; workspace activation pages
are read-only relative to definition.

## Empty states

| Context | Empty state |
|---|---|
| Workspace Sources page, no active sources | "No sources active in this workspace yet. [Browse Global] [+ Add Workspace Source]" |
| Browse Global panel, no globals exist | "Your global library is empty. [Manage Global Library] to add sources you want to reuse across workspaces." |
| Global Sources Library, no globals | "Global sources let you define a source once and activate it in any workspace. [+ New Global Source]" |

## Agent creation: skill-recipe analog for sources

The existing `skill-recipe` skill (added in the skill-recipes work) reasons about which
skills to bundle. Sources need the same treatment so `agent-creator` doesn't blindly attach
every activated source to every new agent.

### `list_sources` session tool

A new session tool, mirroring `list_skills` exactly:

```typescript
list_sources({ activeOnly?: boolean, tags?: string[], search?: string }) → SourceListResult
```

Returns each source's `slug, name, description, tags, type (mcp/api/local), tier (workspace
| global | global-dormant | project), source (workspace/global/project/global-dormant)`.
The `tier` and `source` aliasing matches the `list_skills` output shape. `activeOnly: true`
excludes dormant globals.

### Pattern: source-recipe skill (new starter)

Create a sister skill to `skill-recipe`, named `source-recipe`, with the same shape:

- Description: trigger when an agent is choosing sources for a new agent
- Body: rules for source curation
  - Default cap: **3 sources per agent**. Lower than skills because each source spawns a
    process and adds tool surface area.
  - Match sources to the agent's actual job. Don't bundle Notion if the agent doesn't read
    or write knowledge.
  - Prefer specific over general (e.g., a project's MCP over a generic web-fetch).
  - Don't bundle dormant globals — suggest activating instead.
  - When two sources overlap (e.g., two web-search providers), pick one.

`agent-creator` bundle step now defers to **both** `skill-recipe` and `source-recipe`. The
two are independent — different catalogs, different curation rules.

For implementation, see the existing `skill-recipe` at [packages/shared/src/skills/starter-templates.ts](packages/shared/src/skills/starter-templates.ts)
(`SKILL_RECIPE_SKILL` constant) and mirror it.

## Status indicators

The existing `source-status-indicator` component gets one new state:

- **`global-dormant`** — gray dot, label "Available" — the source is in your global library
  but not activated in this workspace.

Existing states (`connected`, `needs_auth`, `failed`, `untested`, `local_disabled`) all
remain.

## Discoverability nudges

When a workspace has no sources:

> "You haven't activated any sources in this workspace. [Browse global library] to use
> sources you've already set up, or [add a workspace-specific source] for ones unique to
> this project."

When a workspace has many workspace-tier sources that look like duplicates of globals (same
slug):

> "These workspace sources also exist in your global library: notion, github. Consider
> deleting the workspace copies to use the globals — credentials will be inherited."

This nudge fires once per workspace, dismissible. Quality-of-life polish, optional for v1.

## Out of scope

These are deliberately not in v1:

- Editing global sources from a workspace context (always go through Settings → Global
  Sources Library).
- Workspace-tier credential override on a workspace-tier source (no second tier exists below
  workspace).
- Cloud sync of global sources / credentials (local-only filesystem).
- Sharing global sources between users (single-user model).
- A registry to install global sources from (community sources, marketplace, etc.).

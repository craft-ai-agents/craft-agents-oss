## 1. Цель

Превратить десять запретов att2 §18 из однострочного списка в **actionable правила ревью**: для каждой анти-цели зафиксировать, что именно запрещено, почему это запрещено, как обнаружить нарушение (конкретный пункт чек-листа ревью, где возможно — механическая проверка) и какова разрешённая альтернатива. Документ обязателен к применению на каждой волне дорожной карты ([S-09](./09-roadmap-waves.md), критерий приёмки №4).

## 2. Контекст и мотивация

Интеграция двух зрелых интерфейсов почти не имеет технических рисков «не сможем построить» — риски концентрируются в соблазне построить **второй экземпляр** уже существующего (вторая палитра, второй rail, вторая кнопка аккаунта, второй AI-контур) или **магию** (авто-перенос DOM, авто-синхронизация метаданных), которая дешевле сегодня и разрушительна завтра. Оба исходных документа согласованы: att2 §18 (UI-запреты) перекрывается с att1 §5 («что из SiYuan не переносим и скрываем») и att1 §15 (карта решений, включая «Общая универсальная Entity-БД → НЕ строить», «Полная двусторонняя синхронизация метаданных → НЕ строить»). Форк уже содержит все существующие контуры (app-shell, чат, браузер, автоматизации, облачные запуски) — поэтому каждое «два X одновременно» — это не теория, а конкретная пара файлов, которую можно проверить в ревью.

Принцип применения: анти-цель нарушается **кодом и PR**, а не намерением. Поэтому у каждого запрета есть детектор: вопрос чек-листа, grep-паттерн или UI-аудит. Переопределение анти-цели возможно только новым ADR (процесс ADR-001…006, att1 §16/P0), не «в порядке исключения в этом PR».

## 3. Решение: десять анти-целей

### ✗ 1. Две глобальные палитры

- **Что запрещено.** Второй ⌘K-совместимый вход: отдельная палитра внутри embedded SiYuan surface, SiYuan global command palette, показанная пользователю, второй «quick open» в Craft renderer. В системе существует ровно одна глобальная палитра — Craft Omnibox ([S-04](./04-omnibox.md)).
- **Почему.** Две палитры = две ментальные модели «где искать действие», конфликтующие хоткеи и немаршрутизируемые команды вне единого Command Registry (att2 §4). Палитра SiYuan либо скрыта, либо проксирована (att1 §5: «Глобальная палитра команд → скрыть или проксировать»).
- **Как обнаружить.** Чек-лист: «В PR есть второй entry-point палитры?» Механика: grep по renderer на новые обработчики `mod+k`/`cmd+p`/`ctrl+p` вне `actions/registry.tsx` и Command Registry; UI-аудит: ⌘K внутри SiYuan surface открывает Craft-палитру, а не SiYuan-меню.
- **Альтернатива.** `CommandContribution` в Command Registry ([S-04](./04-omnibox.md)); горячая клавиша SiYuan-плагина — команда с `source: "siyuan-plugin"`, маршрутизируемая через global-input-router.

### ✗ 2. Два activity rail

- **Что запрещено.** Вторая вертикальная панель режимов: SiYuan left rail, показанный в integrated mode, отдельный «Knowledge rail» рядом с Craft rail, любой второй столбец иконок режимов вне слота `activity` ([S-01](./01-shell-slots.md)).
- **Почему.** Rail — хозяин глобального режима (att2 §1: «[ГЛОБАЛЬНЫЙ РЕЖИМ] → …»); два хозяина режима = интерфейс внутри интерфейса (att1 §5: «Основная боковая навигация → заменить Craft-навигацией»). Сегодня rail-функцию исполняет мини-навигация `AppShell.tsx` + `LeftSidebar.tsx` — она одна, и переезжает в единый Activity Rail в W1, а не размножается.
- **Как обнаружить.** Чек-лист: «В PR добавлен второй столбец глобальных режимов?» UI-аудит: в любом layout (включая Knowledge mode) ровно один rail; включение integrated SiYuan surface не приводит к видимому SiYuan dock-rail слева (скрытие chrome — обязанность адаптера).
- **Альтернатива.** Режим Knowledge — `PanelContribution {slot: "activity"}` (att2 §9) в том же rail; SiYuan docks проецируются в слоты `navigator-*`/`inspector`/`bottom` по маппингу att2 §9, а не в новый rail.

### ✗ 3. SiYuan AI одновременно с Craft Agent

- **Что запрещено.** Видимый AI-чат/AI-панель SiYuan (включая его настройки моделей) в managed/integrated режиме; параллельная работа двух агентных контуров над одним документом.
- **Почему.** Два агента — два конкурирующих контура разрешений, контекста и биллинга; агентный и исполнительный runtime закреплен за Craft (att1 §2.7), AI chat SiYuan и настройка моделей — «не использовать» (att1 §5). Позиция панели SiYuan AI хорошая — её занимает Craft Agent Inspector (att2 §10).
- **Как обнаружить.** Чек-лист: «В knowledge surface доступны любые UI-точки SiYuan AI (кнопка AI, AI settings, AI dock)?» UI-аудит integrated mode; grep конфигурации default workspace SiYuan на включённые AI-плагины.
- **Альтернатива.** Craft Agent Inspector (`KnowledgeAgentPanel.tsx`, новый компонент, [S-03](./03-panels-rails.md)): contextual companion («Спросить о документе/Переписать блок/Найти источники/Проверить утверждения/Создать связанные заметки») и Full session — оба над существующей Craft-сессией, не новый тип агента (att2 §10).

### ✗ 4. Сторонние расширения в Electron main

- **Что запрещено.** require/import стороннего кода (плагины SiYuan, skill-packs, marketplace-пакеты) в процессе `apps/electron/src/main`; исполнение extension-кода в Craft main по «удобству» (быстрый доступ к Node API).
- **Почему.** Main — trusted first-party контур: падение или компрометация любого стороннего кода там роняет/открывает всё приложение, все сессии и workspace-ы (att2 §8). SiYuan-плагины продолжают исполняться внутри SiYuan runtime — и это единственное их место до L3.
- **Как обнаружить.** Чек-лист: «PR добавляет в `apps/electron/src/main` загрузку кода, не из monorepo?» Механика: ревью импортов main-бандла + lint-правило «main не читает пути из extensions/marketplace dirs»; архитектурный вопрос: «почему это не в extension host?» — обязателен к ответу.
- **Альтернатива.** Extension Host — изолированный процесс с RPC (`extension-host-manager.ts`, новый компонент: no raw secrets, permission checks, resource limits, crash isolation, att2 §8); UI сторонних — sandboxed renderer/iframe (contextIsolation, `nodeIntegration: false`, CSP, typed bridge).

### ✗ 5. Raw API keys расширениям

- **Что запрещено.** Передача расширению/плагину сырых секретов: значений токенов, `process.env`, файла credentials, llm_api_key и т.п. — в любом виде (env vars, аргументы, файлы настроек плагина, IPC-пейлоад).
- **Почему.** Плагин с сырым ключом неограничен и неотзываем; разрешения задуманы capability-образно (att2 §7: `secrets.use:<credential>`), а хранилище секретов уже существует — `CredentialManager` + `SecureStorageBackend` (`packages/shared/src/credentials/{manager,types}.ts`, ключи `{type}::{scope}`).
- **Как обнаружить.** Чек-лист: «Расширение получает что-либо кроме временной capability из identity-broker?» Механика: ревью пейлоадов extension host (нет `process.env`/credential values), ревью `ExtensionManifest.permissions` на предмет обходных запросов; DTO-аудит `BroadcastEventMap`/каналов extensions на секретные поля.
- **Альтернатива.** Временная capability через брокер ([S-07](./07-identity-center.md), `identity-broker.ts`, новый компонент): расширение декларирует `secrets.use:<credential>` в манифесте, пользователь видит это в install flow (att2 §12) и отзывает из Settings→Extensions→Permissions.

### ✗ 6. Авто-перенос DOM любого SiYuan-плагина

- **Что запрещено.** Механическая трансплантация UI плагина в Craft: скрейпинг DOM плагина, пере-рендер его разметки React-компонентами, CSS-инъекции в чужие контейнеры, обещания «любой плагин станет нативным автоматически».
- **Почему.** DOM плагина — его приватный контракт; автоперенос ломается патчем плагина и создаёт иллюзию нативности без настоящих contribution points. Совместимость строится уровнями L0–L3 (att2 §6): то, что нельзя проецировать через адаптер, работает внутри SiYuan surface.
- **Как обнаружить.** Чек-лист: «PR содержит querySelector/CSS-селекторы по разметке SiYuan-плагинов или React-порт чужого DOM?» Также подозрителен любой код, адресующийся к `webContents` знания с инъекцией стилей/скриптов против плагинных узлов (кроме глобального скрытия chrome в integrated mode — это отдельный, строго перечисленный список адаптера).
- **Альтернатива.** Дорога L0 → L1 → L2 → L3 (att2 §6, [S-06](./06-plugin-bridge.md)): L0 «Open in SiYuan compatibility view», L1 запуск из Craft, L2 — экспорт команд/контекстных действий/вкладки/настроек через SiYuan Adapter → Contribution Registry, L3 — переписывание на Craft Extension API самим автором плагина.

### ✗ 7. Объединение Craft Profile и SiYuan Cloud account

- **Что запрещено.** Единая таблица/модель пользователя, сливающая Craft Profile и SiYuan Cloud account; использование SiYuan Cloud как корневой идентичности Craft; требование SiYuan-аккаунта для локальной работы.
- **Почему.** Идентичности разных плоскостей: Craft Profile — хозяин продукта и его workspace-ов, SiYuan Cloud — поставщик sync-услуги знаний. Local-first обязателен: Craft local profile + локальный SiYuan kernel не требуют аккаунта вообще (att2 §11). Объединение навсегда привяжет продукт к чужому billing/availability.
- **Как обнаружить.** Чек-лист: «PR создаёт/расширяет таблицу или модель, где поля Craft Profile и SiYuan Cloud credentials живут как один объект?» Ревью миграций/сторов identity; UI-аудит: один account menu, но SiYuan Cloud виден только как строка `ServiceConnection`.
- **Альтернатива.** Федеративная модель (att2 §11, [S-07](./07-identity-center.md)): `Profile`/`Workspace`/`WorkspaceMembership` + `ServiceConnection {provider: "siyuan-local"|"siyuan-cloud", status: "connected"|"expired"|"syncing"|"error"|"disconnected"}` + `Entitlement`; SiYuan account — в Settings→Accounts & Connections→Knowledge Sync.

### ✗ 8. Labels ↔ tags без явного правила

- **Что запрещено.** Любая автоматическая синхронизация Craft labels и SiYuan tags (в одну или обе стороны): фоновые синкеры, двусторонние маппинги «label X всегда тег #X», запись тегов при смене label вне движка автоматизаций.
- **Почему.** Два домена метаданных разделены физически (ADR-005; att1 §6; [K-02 §6](../2026-08-07-siyuan-integration/02-integration-boundaries.md)): labels — операционная очередь работы, теги — семантика знания. Скрытая синхронизация не видна пользователю, не логируется и порождает петли tag→label→tag между двумя приложениями.
- **Как обнаружить.** Чек-лист (обязателен в PR, трогающих labels/attributes): «Есть ли путь записи SiYuan tags из Craft labels (или наоборот) вне automation engine?» Механика: grep на вызовы setAttribute/tag-мутаций из label-мутаторов (`setLabels`/labels-сторедж) и из knowledge-кода в labels storage; валидный путь ровно один — Automation record.
- **Альтернатива.** Явное automation-правило (att1 §6, [K-10](../2026-08-07-siyuan-integration/10-skills-automations.md), [S-08 §3.5](./08-work-envelope.md)): `WHEN craft.label_added {label:"Publish", target:knowledge} THEN knowledge.set_attribute {workflow: "ready-to-publish"}` — именованное, отключаемое, аудируемое, с явным направлением.

### ✗ 9. Переписывать SiYuan editor

- **Что запрещено.** Новый собственный блочный редактор (ProseMirror/TipTap/Lexical-реализация поверх SiYuan-модели), «временный параллельный editor» на время интеграции, форк редактора SiYuan внутрь monorepo.
- **Почему.** Редактор SiYuan — это блоковая модель + stable block IDs + hierarchy + references + backlinks + attributes + assets + импорт/экспорт; переписывание — многолетний проект внутри проекта и прямое нарушение решения «НЕ переписывать редактор SiYuan. Встраивать как управляемую KnowledgeSurface» (att1 §4.2). Craft встраивает редактор, не заменяет.
- **Как обнаружить.** Чек-лист: «PR добавляет блочный editor-framework или зависимость на него под knowledge UI?» Механика: ревью `package.json` на editor-dependencies и ревью новых renderer-компонентов, рендерящих редактируемый контент документа вне SiYuan webContents.
- **Альтернатива.** Embedded Knowledge Surface: `KnowledgeSurface.tsx` + `knowledge-surface-manager.ts` (новые компоненты) над host-surface паттерном (шаблон `BrowserPanelPage.tsx` + `BrowserPaneManager.createEmbeddedInstance`), события выбора/изменения — через SiYuan Adapter ([S-02](./02-surface-registry-tabs.md), [S-06](./06-plugin-bridge.md)).

### ✗ 10. Отказываться от compatibility view

- **Что запрещено.** Удаление или деградация режима «полный SiYuan UI в Craft-вкладке»: убрать кнопку «Open full SiYuan interface», сделать L0 недоступным «ради чистоты UI», гейтовать compatibility view за фича-флаг, который планируют снять.
- **Почему.** Compatibility view — страховка всей стратегии встраивания: старые плагины, сложные dock-панели, расширенные настройки и диагностика имеют гарантированное место (att2 §13: «Для старых плагинов/сложных dock-панелей/расширенных настроек/диагностики»). Без него любой пробел интеграции становится блокером пользователя и давлением нарушить анти-цели №3/№6/№9.
- **Как обнаружить.** Чек-лист: «PR удаляет/прячет вход в compatibility view или меняет его статус с постоянного режима на временный?» UI-аудит Knowledge mode: вход виден всегда; L0-путь в реестре поверхностей покрыт тестом маршрутизации.
- **Альтернатива.** Compatibility mode как постоянный аварийный/расширенный режим (att2 §13): Knowledge → «Open full SiYuan interface» открывает отдельную Craft-вкладку с полным SiYuan UI; integrated mode остаётся стандартным, compatibility — навсегда доступным.

### 3.11. Сводный чек-лист ревью

Копируется в описание каждого PR волн S ([S-09](./09-roadmap-waves.md)):

```
[ ] 1  Нет второго entry-point палитры (⌘K/⌘P обрабатывает только Command Registry)
[ ] 2  Нет второго столбца глобальных режимов (один activity rail)
[ ] 3  SiYuan AI UI недоступен в integrated mode
[ ] 4  main-процесс не загружает сторонний код
[ ] 5  Расширение получает только broker-issued capability, не raw secrets
[ ] 6  Нет DOM-скрейпинга/React-порта UI SiYuan-плагинов
[ ] 7  Craft Profile и SiYuan Cloud — разные модели (федерация)
[ ] 8  Нет записи labels↔tags вне automation engine
[ ] 9  Нет собственного/форкнутого блочного редактора
[ ] 10 Compatibility view доступен
```

## 4. Границы / что НЕ делаем (мета-правила)

- **НЕ расширяем список без ADR.** Новые анти-цели добавляются через процесс ADR (att1 P0) и правку этого документа, а не устными договорённостями в PR.
- **НЕ переопределяем анти-цель «в одном PR».** Исключение = новый ADR + правка S-10 + ссылка в критериях волны [S-09](./09-roadmap-waves.md).
- **НЕ превращаем чек-лист в бюрократию без детектора.** Каждая анти-цель обязана сохранять пункт «как обнаружить»; правило без детектора не принимается.
- **НЕ применяем анти-цели к suite K-коду**, где тот же запрет сформулирован иначе (конфликт разрешается в пользу более строгой формулировки через [K-02](../2026-08-07-siyuan-integration/02-integration-boundaries.md)).

## 5. Критерии приёмки

- [ ] Все 10 пунктов att2 §18 покрыты подразделами ✗ 1–10 в §3 без пропусков и переформулировок сути.
- [ ] У каждой анти-цели есть: «что запрещено», «почему», «как обнаружить» (чек-лист пункт, где возможно — механическая проверка), «разрешённая альтернатива» со ссылкой на проектный документ.
- [ ] Сводный чек-лист §3.11 копируемым текстом готов к вставке в шаблон PR.
- [ ] Анти-цели не противоречат S-00…S-09 и связанным документам suite K (K-02 §6, K-05, K-10); при расхождении — фиксация в «Открытых вопросах» соответствующего документа.
- [ ] Волны в [S-09](./09-roadmap-waves.md) ссылаются на этот чек-лист как обязательную секцию ревью (критерий приёмки карты №4).

## 6. Открытые вопросы

1. **Скрытие vs удаление SiYuan AI (№3).** Уровень enforcement в external-local режиме ([K-07](../2026-08-07-siyuan-integration/07-connection-modes.md)): рекомендация-заглушка в настройках default workspace или активное сокрытие адаптером? Ответ влияет на силу детектора.
2. **L3-исключение из №6.** Ручной порт конкретного плагина на Craft Extension API его автором — разрешённая дорога (att2 §6); нужен ли формальный whitelist L3-кандидатов, чтобы порт не маскировался под «авто-перенос».
3. **Диагностический SiYuan chrome (№1/№2).** В compatibility view SiYuan-палитра и rail остаются видимыми (это полный SiYuan UI). Формально №1/№2 применимы только к integrated mode — закрепить эту оговорку в формулировках чек-листа или считать compatibility view вне юрисдикции S-10 по определению.
4. **Механизация №8.** Хочется CI-grep «labels→setAttribute outside automations», но доменные пакеты пока внутри `packages/core` (att2 §16) — границы для grep-правила появятся только после W1/W2; до тех пор детектор чисто ревьюерский.

## 1. Цель

Оформить шесть решений фазы P0 как архитектурные decision records. ADR — единственный «непереоткрываемый» слой suite K: любой документ 02–11 и любой документ suite S, противоречащий ADR, исправляется сам; изменение ADR требует явного пересмотра с указанием статуса (`Superseded by …`).

ADR не дублируют детали подсистем: каждое решение ссылается на документы, где оно раскрыто операционально.

## 2. Контекст и мотивация

Интеграция двух зрелых систем соблазняет к «быстрым» решениям с долгими последствиями: встроить SiYuan целиком как есть, слить базы, дать агенту прямой SQL-доступ, синхронизировать labels↔tags в фоне. Каждый такой шаг необратимо дорог: миграции данных, лицензионные риски, скрытая порча долговечных знаний. Фаза P0 («Вердикт», §16) фиксирует шесть решений до начала реализации, чтобы подсистемные PRD проектировались внутри заданных ограничений, а не переизобретали их.

Формат каждого ADR: **Статус · Контекст · Решение · Последствия (позитивные/негативные) · Альтернативы и почему отклонены**.

## 3. Решение

### ADR-001. Craft is host product

**Статус**: Accepted (P0, 2026-08-07)

**Контекст.** Есть два продукта с пересекающимися оболочками: форк `agisota/craft-agents-oss` (347 коммитов вперёд, 1 позади относительно upstream; собственные контуры `packages/cloud-runner`, `apps/cloud-gateway`, `packages/messaging-discord-worker`) и SiYuan (зрелый knowledge kernel: блоки, backlinks, атрибуты, базы данных, SQL). Нужно выбрать магистраль: чья оболочка, чья навигация, чей runtime определяет продукт.

**Решение.** Craft остаётся главным приложением, продуктовым интерфейсом и исполнительным ядром. SiYuan поглощается как специализированный движок знаний: его app shell, боковая навигация, workspace-switcher, AI chat и настройки моделей скрываются или заменяются Craft-аналогами (карта — [02-integration-boundaries.md](./02-integration-boundaries.md) и suite S [01-shell-slots.md](../2026-08-07-unified-shell/01-shell-slots.md)). Ничего из Craft в SiYuan не переносится.

**Последствия.**
Позитивные:
- Продукт сохраняет единую идентичность и UX; вложения форка (347 коммитов) не обесцениваются.
- Агентный runtime, сессии, permissions (`packages/shared/src/agent/permissions-config.ts`), облачные запуски и мессенджерные шлюзы продолжают эволюционировать без повторного проектирования.
- Один shell = один слой поддержки: нет «интерфейса внутри интерфейса».

Негативные:
- Вся ответственность за интеграционный UX ложится на команду Craft (скрытие chrome SiYuan, маршрутизация горячих клавиш, статус-бар синхронизации).
- Функции SiYuan-оболочки, которые пользователи любят (граф, docks), придётся явно проецировать в Craft-реестры — это работа suite S, а не «бесплатный» перенос.
- Расхождение с upstream Craft будет расти: каждое интеграционное решение увеличивает стоимость будущих ребейзов.

**Альтернативы.**
- *SiYuan как хост, Craft как плагин.* Отклонено: у SiYuan нет агентного runtime, сессий, cloud-runner, browser-контура, permissions-модели уровня Craft; потребовался бы перенос практически всех 347 коммитов ценности форка в чужую кодовую базу.
- *Два равноправных приложения бок-о-бок (deep links).* Отклонено: два shell, две палитры, два AI-чата, два account-switcher — ровно тот «интерфейс внутри интерфейса», который снимает вердикт; контекст не переносится между приложениями без костылей.
- *Третий продукт (новый shell поверх обоих).* Отклонено: обесценивает обе существующие кодовые базы и множит тестовую поверхность без добавленной ценности.
- *Физический merge двух кодовых баз.* Отклонено на этом этапе: разные стеки и лицензии (Apache-2.0 × AGPLv3 — см. [08-licensing.md](./08-licensing.md)); зафиксировано как анти-решение в карте [00-overview.md](./00-overview.md) §3.4.

### ADR-002. SiYuan owns canonical knowledge

**Статус**: Accepted (P0, 2026-08-07)

**Контекст.** Интеграции знаний чаще всего проваливаются на дублировании: продукт копирует документы в своё хранилище «для скорости» и получает две правды, конфликты версий и невозможность ответить «где канонический источник?». У SiYuan уже реализовано то, что пришлось бы писать с нуля: notebook tree, document tree, стабильные block IDs, иерархия блоков, block references, backlinks, индексы, поиск, атрибуты, SQL, database views, assets, import/export.

**Решение.** SiYuan — единственная система записи для знаний. Craft **не пишет** своё блочное хранилище и свой граф обратных ссылок. Craft хранит только интеграционное состояние (снапшоты контекста, cross-links, proposals, публикации, аудит — схема в [04-bridge-storage.md](./04-bridge-storage.md)). Доступ к знаниям — исключительно через `KnowledgeProvider` ([03-knowledge-provider-contract.md](./03-knowledge-provider-contract.md)); кеши допустимы только инвалидационные, без претензии на каноничность.

**Последствия.**
Позитивные:
- Один источник правды о контенте: экспорт, мобильные клиенты и синхронизация SiYuan продолжают работать поверх тех же данных.
- Не нужно реализовывать и поддерживать backlinks/SQL/search — многолетняя работа SiYuan используется как есть.
- Чистая граница ответственности: порча данных локализуется в одной системе.

Негативные:
- Доступность знаний = доступность SiYuan kernel; его падение делает Knowledge mode деградированным (нужны health-check и честные статусы — [07-connection-modes.md](./07-connection-modes.md)).
- Горячие пути (рендер списков, mention-picker) чувствительны к IPC/HTTP-задержкам — требуются кеши и page-пагинация в адаптере.
- Мажорные миграции формата SiYuan становятся нашим эксплуатационным риском.

**Альтернативы.**
- *Собственное блочное хранилище в Craft.* Отклонено: дублирование зрелого kernel (backlinks, SQL, database views, assets) — месяцы работы и вечный долг сравнения реализаций.
- *Полная копия знаний в storage Craft с фоновой синхронизацией.* Отклонено: двусторонняя синхронизация — анти-решение карты (§3.4 [00-overview.md](./00-overview.md)); конфликты, инвалидность, невозможность audit.

### ADR-003. No shared database

**Статус**: Accepted (P0, 2026-08-07)

**Контекст.** Кажется естественным «слить модели»: одна Entity-БД, общие таблицы для sessions/documents/runs. В кодовой базе Craft каноническое состояние сегодня — JSONL/MD-файлы (`packages/shared/src/sessions/storage.ts`, `packages/server-core/src/sessions/SessionManager.ts`); единственный SQLite — fail-soft FTS5-проекция `packages/server-core/src/memory/fts-index.ts`, без ORM и без миграционного тулинга. Слияние с SQLite-миром SiYuan означало бы редизайн обоих хранилищ.

**Решение.** Общей базы нет: Craft storage и SiYuan workspace разделены HTTP/process-границей. Bridge-BД хранит **только интеграционное состояние** — шесть таблиц: `knowledge_connections`, `knowledge_context_snapshots`, `knowledge_links`, `knowledge_mutation_proposals`, `knowledge_publications`, `knowledge_audit_log` (DDL и инварианты — [04-bridge-storage.md](./04-bridge-storage.md)). Принцип: «единая поверхность отображения ≠ единая каноническая модель данных» — UI может быть общим ([09-collection-view-engine.md](./09-collection-view-engine.md)), данные — нет.

**Последствия.**
Позитивные:
- Независимые жизненные циклы и миграции: обновление SiYuan не требует миграции Craft storage и наоборот.
- Чистая лицензионная граница (процесс + API) — критично до решения [08-licensing.md](./08-licensing.md).
- Минимальная поверхность Bridge легко тестируется и аудируется (conformance на шесть таблиц).

Негативные:
- Запросы «в одном списке показать сессию + документ + run» решаются проекциями в UI-слое, а не JOIN — дополнительный код сведения ([09-collection-view-engine.md](./09-collection-view-engine.md)).
- Нет распределённых транзакций: согласованность «публикация документа + cross-link» достигается идемпотентными шагами и reconciler'ами, а не 2PC.
- Health/паритет состояния двух систем нужно эксплуатировать явно (connection health, version check — P1).

**Альтернативы.**
- *Прямое открытие SQLite SiYuan из Craft.* Отклонено: привязка к внутренней схеме (ломается релизами kernel), обход API и блокировки/race с пишущим kernel, невозможность валидации записей.
- *Универсальная Entity-БД (одна схема на sessions/documents/runs/skills).* Отклонено: big-bang редизайн обоих миров; анти-решение карты §3.4 [00-overview.md](./00-overview.md).

### ADR-004. All agent writes use proposals

**Статус**: Accepted (P0, 2026-08-07)

**Контекст.** Агент с прямым `updateBlock()` способен молча испортить долговечные знания — и обнаружено это будет после синхронизации на все устройства. MCP как канал записи не решает проблему: интерфейс зависит от модели, сложно показать точный diff, обеспечить атомарность и отловить конфликты («Вердикт», §10). При этом read-only интеграция (P1) уже даёт ценность без риска.

**Решение.** Любая запись в SiYuan идёт через мутационный конвейер: `READ TARGET → CAPTURE BASE HASH → AGENT GENERATES PATCH → SHOW CRAFT DIFF → USER APPROVES → RE-READ TARGET → HASH MATCHES ? APPLY + AUDIT + INVERSE PATCH : CONFLICT` (полный контур — [05-mutation-safety.md](./05-mutation-safety.md)). Интерфейс: `proposeMutation()` / `applyMutation()` в `KnowledgeProvider` ([03-knowledge-provider-contract.md](./03-knowledge-provider-contract.md)). На старте разрешены только: create document, append block, update explicitly selected block, set explicitly selected attribute. Запрещены: bulk delete, notebook delete, arbitrary SQL write, mass update, silent overwrite. Каждый apply пишет audit-запись и inverse patch для rollback.

**Последствия.**
Позитивные:
- Пользователь всегда видит, что именно изменится; база знаний защищена от «тихой» порчи.
- Конфликты конкурентного редактирования ловятся base-hash проверкой, а не замечаются постфактум.
- Audit + inverse patch → rollback — первоклассная операция, а не ручное восстановление.
- Повторяемая, тестируемая машина состояний proposal: `draft → approved → applied | conflict | rolled-back`.

Негативные:
- Дополнительный шаг в UX: агент «сделал» ≠ изменение в базе; нужен честный diff-UI (diff surface, suite S [02-surface-registry-tabs.md](../2026-08-07-unified-shell/02-surface-registry-tabs.md)).
- Двойное чтение (до и после одобрения) добавляет задержку и нагрузку на kernel.
- Allow-list ограничивает «умные» автоматизации: частые легитимные паттерны (например, rename heading по дереву) потребуют расширения allow-list через отдельный review.

**Альтернативы.**
- *Прямая запись в Auto/execute permission mode.* Отклонено на первой версии: silent corruption недетектируема до синхронизации; режимы разрешений Craft (`PermissionModes`: explore/ask/execute, `packages/shared/src/agent/mode-types.ts`) не достаточно гранулярны для долговечных данных.
- *MCP write-tools как единственный путь записи.* Отклонено: §10 вердикта — непрозрачный write-back, сложность атомарности/конфликтов; MCP остаётся агентной поверхностью, системная — `KnowledgeProvider`.
- *Оптимистичная запись с пост-проверкой.* Отклонено: откат после возможной синхронизации на устройствах пользователя не гарантирован.

### ADR-005. Operational and semantic metadata remain separate

**Статус**: Accepted (P0, 2026-08-07)

**Контекст.** У Craft и SiYuan — разные природы метаданных. Craft (операционные): `work.status/labels/priority/flagged/assignee/queue/review_state` — «что сейчас происходит с работой?»; они живут в существующих моделях (`SessionConfig.labels/sessionStatus/isFlagged/isArchived` — `packages/shared/src/sessions/types.ts`; labels engine — `packages/shared/src/labels/`). SiYuan (семантические): `knowledge.tags/type/author/topic/valid_from/source/rating` — «что это за знание?»; они живут в атрибутах kernel. Фоновая двусторонняя синхронизация таких полей — классический источник петель и потери данных.

**Решение.** Два namespace метаданных физически разделены (следствие ADR-003) и **не синхронизируются автоматически**. Отображаться могут в одном инспекторе (секции WORK / KNOWLEDGE). Пересечение — только через явную пользовательскую автоматизацию, например: `WHEN Craft label=Publish THEN set SiYuan attr.workflow=ready-to-publish` ([10-skills-automations.md](./10-skills-automations.md)). Для удобства представлений Craft хранит «рабочий конверт» `KnowledgeWorkEnvelope` (status/labels/flagged/assignedTo поверх `KnowledgeRef`) — деталь в suite S [08-work-envelope.md](../2026-08-07-unified-shell/08-work-envelope.md); конверт — данные Craft, не копия атрибутов SiYuan.

**Последствия.**
Позитивные:
- Нет скрытых sync-циклов: каждое перетекание метаданных — осознанное правило, видимое в автоматизациях пользователя.
- Обе системы эволюционируют свободно: новый label в Craft не требует миграции атрибутов SiYuan.
- Инспектор показывает обе системы полей рядом без претензии на единую схему.

Негативные:
- Пользователь видит два набора полей — нужна дисциплина copy и нейминга (разные заголовки секций, подсказки «где что живёт»).
- Реальные кросс-доменные желания («покрасить документ по сессионному статусу») требуют ручной настройки автоматизации.
- Возможно визуальное «расхождение» между envelope и атрибутами — интерфейс обязан помечать, какое поле откуда.

**Альтернативы.**
- *Полная двусторонняя синхронизация labels↔tags.* Отклонено: конфликты namespace (у Craft labels — дерево с типизированными значениями, `id::value`; у SiYuan tags — плоские), петли «sync-triggered-sync», анти-решение карты §3.4 [00-overview.md](./00-overview.md).
- *Единая объединённая схема метаданных.* Отклонено: нарушает ADR-003 (общая база) и смешивает разные жизненные циклы (оперативное vs долговечное).

### ADR-006. Session is not a document

**Статус**: Accepted (P0, 2026-08-07)

**Контекст.** Session — процесс работы: messages, turns, tool calls, streaming, model/provider, permission mode, status, labels, archive, timestamps; канонический владелец — Craft (`packages/shared/src/sessions/types.ts`, `packages/shared/src/sessions/storage.ts` — JSONL-журнал). Document — принятый результат работы, курируемое долговечное знание. Автоматическое превращение транскриптов в документы засоряет базу знаний сырым шумом; аналогично Craft Memory (рабочая/эпизодическая память, `packages/server-core/src/memory/`) не равна базе знаний.

**Решение.** История чатов и память **не переносятся** в SiYuan. Связь миров — явная: Session → linked knowledge blocks, generated artifacts, published document. Поток знания: `Session/Run → Craft memory → distillation → review → SiYuan knowledge`, где публикация — отдельный контур с distill skill, review/diff, выбором notebook/path и provenance (`source_session_id`, `source_run_ids`, `generated_by`, `source_blocks`) — спецификация в [06-publication-pipeline.md](./06-publication-pipeline.md). Отношение «session ↔ document» — many-to-many через `knowledge_links` и cross-links ([04-bridge-storage.md](./04-bridge-storage.md)).

**Последствия.**
Позитивные:
- База знаний остаётся курируемой: в неё попадает только то, что прошло distill + review.
- Provenance формализован: каждый опубликованный документ отвечает «из какой сессии/ранов/модели он родом»; сессия показывает «Published to: …».
- Разные retention-политики: транскрипты могут архивироваться/гнить, документы — нет.

Негативные:
- Публикация — отдельный пользовательский шаг (трение); пользователи, ожидающие «всё само сохранилось в вики», должны получить понятный entry-point.
- Качество попадающего в базу зависит от качества distill-skill — требуется итеративная работа над его промптами.
- Нужно поддерживать и показывать связи в обе стороны (сессия → документ, документ → сессии), иначе provenance становится мёртвым полем.

**Альтернативы.**
- *Автодамп каждой сессии в SiYuan.* Отклонено: «НЕ автовываливать каждое наблюдение в базу знаний» — база превращается в помойку транскриптов, поиск по знаниям деградирует.
- *Session == SiYuan Document (один тип сущности).* Отклонено: конфликт жизненных циклов (append-only журнал процесса против редактируемого результата), невозможность каноничных backlinks по процессу.
- *Перенос сессий в SiYuan на этапе архивации.* Отклонено: ломает существующие механизмы Craft (archive/unread/share — `SessionManager.ts`) и не решает задачу «принятый результат».

## 4. Границы / что НЕ делаем

- ADR не вводят новых пакетов и не предписывают конкретных имён файлов — целевая структура модулей описана в [02-integration-boundaries.md](./02-integration-boundaries.md) и в подсистемных документах.
- ADR не отменяют существующие конвенции репозитория (i18n через `t()` во всех 10 локалях, классификация RPC-каналов в `packages/shared/src/protocol/routing.ts` и т.д.) — они дополняют их knowledge-спецификой.
- ADR не фиксируют roadmap-порядок — это [11-roadmap.md](./11-roadmap.md); здесь только решения и их обоснование.
- Пересмотр ADR не делается «по ходу задачи»: только отдельным решением со статусом `Superseded` и ссылкой на заменяющий ADR.

- [ ] Каждый ADR содержит: Статус (Accepted, P0, 2026-08-07), Контекст, Решение, Последствия (позитивные и негативные), Альтернативы с причинами отказа.
- [ ] Каждый ADR ссылается на документы suite K, где решение раскрыто операционно (02–06, 08–10), и/или на suite S.
- [ ] Утверждения о существующем коде снабжены реальными путями (`packages/shared/src/...`, `packages/server-core/src/...`).
- [ ] Ни одно решение не противоречит карте решений [00-overview.md](./00-overview.md) §3.4.
- [ ] Раздел «Границы» явно запрещает ad-hoc пересмотр ADR.

## 6. Открытые вопросы

1. **Политика изменения режима записи.** Когда/если прямой write-back без обязательного approval станет допустимым для узкого allow-list (например, только append в inbox-notebook)? Требует отдельного ADR (потенциальный ADR-007) с метриками инцидентов P3.
2. **Superseded-процесс.** Формальные поля пересмотра (`Superseded by`, дата, причина, список затронутых документов) определить при первом реальном пересмотре любого ADR.
3. **Machine-readable ADR.** Нужен ли машинно-читаемый реестр ADR (front-matter), чтобы CI проверял ссылки из кода (например, комментарий `// ADR-004` рядом с proposal-конвейером)? Отложено до P3.
4. **Привязка P0 к волнам shell.** ADR-001/005 имеют прямые следствия в suite S (слоты, envelope); согласование стадий P0–P7 с волнами W1–W6 — в [11-roadmap.md](./11-roadmap.md) и suite S [09-roadmap-waves.md](../2026-08-07-unified-shell/09-roadmap-waves.md).

## 1. Цель

Зафиксировать лицензионную рамку интеграции Craft (Apache-2.0) с SiYuan (AGPLv3): четыре возможных варианта с последствиями и обоснованную рекомендацию; жёсткое правило поведения до принятия юридического решения; список разрешённых и запрещённых интеграционных приёмов по каждому режиму подключения ([07-connection-modes.md](./07-connection-modes.md)); сформулированный список вопросов для юридической консультации.

Это **рамка для решения**, а не само решение: финальное слово за юристом, но инженерные фазы P1–P6 обязаны быть спроектированы так, чтобы не зависеть от его исхода.

## 2. Контекст и мотивация

Исходная раскладка лицензий:

| Компонент | Лицензия | Как доставляется пользователю |
|---|---|---|
| Craft (форк `agisota/craft-agents-oss`, upstream `craft-agents-oss`) | Apache-2.0 | Наши релизы dmg/zip, исходники в публичном репо |
| SiYuan kernel + UI (`siyuan-note/siyuan`) | AGPL-3.0 | Пока — установка самим пользователем; после P7 возможно — наша дистрибуция |
| Код интеграции (knowledge-bridge внутри Craft monorepo) | Apache-2.0 (как часть Craft) | В наших релизах |

Два соображения делают тему блокирующей для managed-режима:

1. **Тезис вердикта:** «отдельный процесс ≠ автоматически никаких AGPL-обязательств». Процессная изоляция (Craft ↔ HTTP ↔ SiYuan kernel) — сильный аргумент в пользу «at arm's length» взаимодействия, но не формальная гарантия: граница «combined work vs mere aggregation» определяется теснотой связки (семантическая зависимость, единый интерфейс, совместная дистрибуция, управление жизненным циклом), а не фактом раздельных процессов как таковым.
2. **Асимметрия режимов.** External-local и remote не распространяют код SiYuan вообще — рисковая зона узкая. Managed упаковывает бинарь ядра в установщик Craft и управляет им — это распространение AGPL-компонента в одном продукте с Apache-кодом, и вопрос copyleft-охвата встаёт в полный рост.

Дополнительный практический контекст: продукт имеет закрытый/коммерческий горизонт (собственный канал обновлений, подписанные дистрибутивы), поэтому вариант «весь продукт под AGPL» — стратегическое решение, а не техническое умолчание.

Жёсткая связка с дорожной картой (см. [11-roadmap.md](./11-roadmap.md) и §3.9 в [07-connection-modes.md](./07-connection-modes.md)):

> **Фазовая связка:** `external-local` (и опционально `remote`) — вариант A ниже — покрывают фазы P1–P6 целиком, без какой-либо дистрибуции кода SiYuan. `managed` — фаза P7 — запускается только после принятого лицензионного решения (вариант B или C).

## 3. Решение

### 3.1 Исходная правовая рамка

- **Apache-2.0 (Craft)**: permissive, патентный грант, свободное коммерческое использование и релицензирование производных при сохранении NOTICE. Совместима «впитыванием» в copyleft (AGPLv3), но не наоборот: Apache-код может войти в AGPL-продукт, AGPL-код не может войти в Apache-продукт без переноса обязательств.
- **AGPL-3.0 (SiYuan)**: copyleft с §13 (Remote Network Interaction — источник обязан предоставляться пользователям, взаимодействующим по сети) и §6 (Installation Information / anti-Tivoization — релевантно для подписанных дистрибутивов и сторов).
- Следствие: любой контур, в котором Craft **распространяет** или **модифицирует** SiYuan, требует либо AGPL-совместимой публикации затронутых частей с source offer, либо коммерческого разрешения правообладателя (Yunnan Liandi / siyuan-note).

### 3.2 Четыре варианта

Сводная таблица (детальный разбор каждого — ниже):

| # | Вариант | Что происходит юридически | Последствия для продукта/кода | Риск | Режимы |
|---|---|---|---|---|---|
| **A** | Внешний SiYuan: пользователь ставит и обновляет SiYuan сам; Craft общается по публичному HTTP API | Craft ничего не распространяет из SiYuan; взаимодействие по сетевому API — позиция «at arm's length»; приемлемость почти общепризнана, но формально не судебно урегулирована | Ноль упаковки; поддержка диагностики версий; окно совместимости; пользователь несёт шаг установки | Низкий (форма взаимодействия), остаточный — теоретическая претензия к «combined work» по тесноте API-зависимости | `external-local`, `remote` |
| **B** | Открытый объединённый продукт: бандлим SiYuan kernel в установщик и публикуем весь связанный объём AGPL-совместимо | Мы распространяем AGPL-компонент в составе продукта → затронутые части (потенциально весь связанный объём) выпускаются под AGPL-совместимой схемой с source offer и полными текстами лицензий | Требуется: публикация исходников продуктового связанного объёма, процесс source offer, NOTICE/LICENSE маркировка, нельзя закрытый релизный контур для этого объёма; §6 anti-Tivoization конфликтует с закрытыми подписанными билдами/сторами | Средний (процессный) + стратегический (открытость продукта) | `managed` |
| **C** | Коммерческое разрешение: договор с правообладателем SiYuan (Yunnan Liandi) на OEM/встраивание и распространение kernel | AGPL-обязательства снимаются договором для согласованного объёма; Craft сохраняет Apache-2.0 контур и возможные закрытые релизы | Договор, возможно royalties/подписка; технические условия (версии, патч-политика, товарный знак) фиксируются в договоре; процессно — самый простой путь для managed | Низкий юридический (при договоре), коммерческий (условия/зависимость от поставщика) | `managed` |
| **D** | Замена kernel: собственная реализация блочного хранилища/бэклинков/SQL/DB-views или сторонний движок под permissive-лицензией | Правовой вопрос исчезает ценой полного инженерного бюджета | Противоречит фундаментальному решению интеграции (вердикт: «Craft НЕ пишет своё блочное хранилище и свой граф обратных ссылок»); многомесячная разработка, потеря совместимости экосистемы SiYuan | Высокий инженерный, низкий юридический | любой (выход из SiYuan) |

**Вариант A — внешний SiYuan (рекомендуемый базис).** Craft релизится как чистый Apache-2.0 продукт; SiYuan — отдельная программа пользователя. Коммуникация — HTTP API на loopback/через TLS; Craft не знает и не должен знать о внутренностях ядра больше, чем знает любой HTTP-клиент. Аргументы за: отсутствие дистрибуции AGPL-кода; отсутствие модификаций; общепринятая трактовка взаимодействия по публичному API как «at arm's length»; SiYuan сам публично позиционирует свой HTTP API как интеграционный. Остаточный риск: экстенсивное прочтение copyleft по «тесной семантической зависимости» — гасится тем, что (а) API документирован и публичен, (б) Craft функционирует и без SiYuan (подключение опционально), (в) мы не адаптируем SiYuan под Craft и не ставим его в дистрибутив. Погасить окончательно — вопросом №1 юристу (§6).

**Вариант B — открытый объединённый продукт (fallback при выборе «открытого продукта»).** Если стратегия продукта открытая, бандлинг ядра легален при AGPL-совместимой публикации: публикуем исходники связанного объёма, `Source Offer`, полные тексты лицензий в дистрибутиве, маркировку файлов. Ограничения: (1) §6 anti-Tivoization — подписанные нотаризованные билды и, тем более, сторы с DRM несовместимы в строгом прочтении (для десктопа с пользовательскими средствами пересборки — спорно, для iOS/App Store — практический блокер); (2) закрытый коммерческий канал для связанного объёма исчезает — это стратегическая цена.

**Вариант C — коммерческое разрешение (предпочтительный для managed).** У siyuan-note существует практика коммерческого лицензирования; OEM-договор решает вопрос полностью: распространение kernel внутри Craft, сохранение Apache-2.0/закрытых релизов, согласованная политика версий и патчей. Риски — коммерческие: цена, условия пересмотра, зависимость от поставщика (гасится тем, что вариант A остаётся рабочим — выход из договора = возврат к external-local).

**Вариант D — замена kernel (последний резорт).** Юридически чисто, инженерно — отказ от базового решения интеграции (вердикт, §4.1: блоковое хранилище, стабильные ID, бэклинки, SQL, DB views, editor — всё SiYuan; «твой Craft» пишет платформу, а не хранилище). Рассматривается только если C недоступен, а B несовместим со стратегией, и при этом доказано, что знания без SiYuan недостижимы.

### 3.3 Рекомендация

1. **Сейчас и для P1–P6 — только вариант A** (`external-local`, опционально `remote`). Он сохраняет статус-кво лицензий, не требует ни письма юристу до старта, ни каких-либо изменений в релизном контуре, и не закрывает ни один из будущих путей.
2. **Для managed (P7) — сначала пробуем вариант C** (коммерческое/OEM-разрешение): запрос правообладателю инициируется при входе в P6, чтобы договорённость (или отказ) была на руках к гейту P7.
3. **B — контролируемый fallback**: выбирается только осознанным стратегическим решением «продукт открытый», с руководимым процессом публикации (§3.7), а не молчаливым бандлингом.
4. **D — только по эскалации** (недоступность C и неприемлемость B).

Обоснование последовательности: вариант A независим от исхода юридического вопроса, поэтому интеграция не простаивает; P7 — единственный пункт, где требуется решение, и к нему ответ уже получен (инициация в P6).

Дерево решений:

```
P1–P6 (сейчас) ───────────────────► вариант A: external-local (+ remote),
                                    релиз без единого байта SiYuan
P7: нужен managed? ── нет ─────────► остаёмся на варианте A бессрочно
   │ да
   ▼
Консультация юриста + переговоры (инициация на входе в P6)
   ├── OEM-договор достигнут ──────► вариант C: бандлим kernel, контур Craft не меняется
   ├── OEM нет, продукт открыт ────► вариант B: AGPL-совместимая публикация связанного объёма
   └── ни C, ни B приемлемо ───────► P7 не стартует; эскалация — вариант D (замена kernel)
```

При любом исходе P1–P6 не переделываются: выбор варианта влияет только на то, кто и как упаковывает ядро, но не на API-контракт интеграции ([07-connection-modes.md](./07-connection-modes.md) §3.9).

### 3.4 Жёсткое правило до решения

> **До разрешения лицензионного вопроса в monorepo НЕ копируется никакой код SiYuan** — ни исходники (Go/TS/SQL), ни сгенерированные из них артефакты, ни бинари ядра, ни UI-компоненты. Работаем через публичный HTTP API и встраиваемую поверхность (host surface: живой UI, отдаваемый внешним процессом, — см. [../2026-08-07-unified-shell/02-surface-registry-tabs.md](../2026-08-07-unified-shell/02-surface-registry-tabs.md); прецедент хостинга — `BrowserPaneManager.createEmbeddedInstance`).

Следствия правила для процесса:

- Типы клиента SiYuan API пишутся **clean-room** по публичной документации API (собственные TypeScript-интерфейсы в `packages/knowledge-siyuan/`, новый компонент), без копирования сигнатур из исходников SiYuan.
- Любой PR, затрагивающий `packages/knowledge-siyuan/**`, снабжается подтверждением «код не производный от кода SiYuan» (чек-бокс в шаблоне PR; новый процессный компонент).
- CI-гейт: сканер запрещённых путей/маркеров (предложение, новый компонент): проверка отсутствия файлов с AGPL-заголовками и строк `siyuan-note/siyuan` в исходниках (кроме этой документации и ссылок). Автоматика предлагается; список маркеров — приложение к решению юриста.

### 3.5 Разрешённые и запрещённые интеграционные приёмы

| Приём | Статус | Комментарий |
|---|---|---|
| Обращение к публичному HTTP API SiYuan (loopback/TLS) | ✅ разрешён | Основа всех режимов ([07-connection-modes.md](./07-connection-modes.md)) |
| Clean-room TypeScript-типы по публичной API-документации | ✅ разрешён | Без импорта из репозитория SiYuan |
| Встраивание живого UI SiYuan через host surface (BrowserView из внешнего процесса) | ✅ разрешён | Код не копируется; контент отдаёт процесс пользователя/сервера |
| Авто-детект установленного SiYuan (probe `localhost:6806`) | ✅ разрешён | Только probe сетевой точки версии, без записи в ядро |
| Ссылки на официальные сайт/доки/репозиторий SiYuan в инструкциях | ✅ разрешён | Номинативное упоминание |
| (->) Хранение токена через `CredentialManager` (`source_apikey`) | ✅ разрешён | Юридически нейтрально, см. §3.6 в [07-connection-modes.md](./07-connection-modes.md) |
| Импорт/копирование любого кода из `siyuan-note/siyuan` в monorepo | ❌ запрещён до решения | Включая «маленькие утилиты», SQL и схемы |
| Вендоринг бинаря/скриптов kernel в релиз dmg/zip | ❌ запрещён до решения | Это и есть дистрибуция AGPL-артефакта (=вариант B/C) |
| Форк UI-компонентов SiYuan / оборачивание их CSS/JS | ❌ запрещён до решения | Host surface покрывает потребность без копирования |
| Модификация SiYuan (патчи ядра) с распространением или сетевым предоставлением | ❌ запрещён до решения | §13 AGPL делает источник обязательным даже при SaaS |
| Копирование документации SiYuan в нашу вики/доки | ❌ запрещён | Ссылки — да, копирование — нет (author's copyright) |

**Дистрибуция по режимам:**

- `external-local` — распространяется только Craft (Apache-2.0); SiYuan ставит и обновляет пользователь. Обязательств по AGPL для нашего релиза: нет (при принятии позиции варианта A; подтверждение — вопрос №1).
- `remote` — мы ничего SiYuan'овского не распространяем (сервер — собственность пользователя). Особый случай: если Craft когда-либо сам будет **хостить** модифицированный SiYuan как сервис для пользователей — включается AGPL §13 (source offer для сетевых пользователей); в текущем скоупе такого хостинга нет (см. §4).
- `managed` — установщик содержит бинарь SiYuan kernel → **без решения не выпускается**; при решении — по варианту B (AGPL-совместимая публикация + source offer) или C (OEM-договор). До P7 в релизной цепочке managed вообще нет (порядок внедрения — §3.9 в [07-connection-modes.md](./07-connection-modes.md)).

### 3.6 Связка с фазами и гейт P7

- **P0 (ADR)**: фиксируется целевой лицензионный принцип — «все работы P1–P6 выполняются в рамках варианта A; managed подлежит отдельному лицензионному решению» (оформление — ADR в [01-adrs.md](./01-adrs.md)).
- **P1–P6**: только `external-local`/`remote`; в релизах нет ни одного байта SiYuan; контур записи ([05-mutation-safety.md](./05-mutation-safety.md)) и все остальные контуры проектировать так, чтобы они не требовали модификаций ядра.
- **P6 (на входе)**: инициируется запрос коммерческого разрешения (вариант C) и/или юридическая консультация по варианту B — так, чтобы ответ был к гейту P7.
- **P7 (гейт)**: выпуск managed возможен только при выполненном одном из: (а) подписанное OEM-разрешение; (б) руководимая AGPL-совместимая публикация (вариант B) с процессом §3.7. Иначе P7 не стартует.

### 3.7 Compliance-чеклист при переходе к распространению (B/C)

Применяется только когда/если managed вошёл в релиз:

- [ ] В установщик включены: полный текст AGPL-3.0, NOTICE-файл SiYuan, наш файл-опись сторонних компонентов.
- [ ] Вариант B: публичный репозиторий/архив исходников распространяемого объёма, `Source Offer` в установщике и на сайте; процесс обновления исходников при каждом релизе.
- [ ] Вариант B: отсутствие DRM/стор-ограничений на установку пользователем собственных сборок затронутого объёма (§6) — проверить для каждого канала (dmg/zip/App Store).
- [ ] Вариант C: действующий договор, объём (версии, платформы, патчи) в пределах договора; отслеживание истечения/пересмотра.
- [ ] Любые наши патчи к ядру (если появятся): вариант B — опубликованы; вариант C — покрыты договором; до решения — не существуют (§3.5).

## 4. Границы / что НЕ делаем

- **Не релицензируем Craft**: Apache-2.0 остаётся лицензией нашего кода при всех вариантах, кроме осознанно выбранного B (и тогда — только связанный объём по заключению юриста).
- **Не принимаем юридическое решение в инженерных документах**: эта спека — рамка; финальное решение фиксируется ADR после консультации.
- **Не откладываем P1–P6 в ожидании юриста** — вариант A для этого и выбран.
- **Не бандлим и не скачиваем бинарь SiYuan** ни в одном релизе до P7-гейта (включая «временные» dev-сборки для внутреннего тестирования managed — dev-host держит внешний SiYuan).
- **Не модифицируем SiYuan** и не ведём свой форк его кода до решения (включая «просто поправить API» — такие потребности эскалируются upstream).
- **Не даём правовых гарантий пользователям** в продуктовых текстах («можно ли коммерчески использовать связку») — только ссылки на лицензии обоих продуктов.
- **Не хостим SiYuan как сервис** от имени пользователей (иначе включается §13; любой такой замысел — отдельное решение).
- **Не выносим управляемое ядро в cloud-run окружение** (Cloudflare/Modal): managed-режим определён только для локальной машины пользователя ([07-connection-modes.md](./07-connection-modes.md) §3.4); исполнение ядра на нашей облачной инфраструктуре — это распространение и сетевое предоставление одновременно, и рассматривается отдельно от этой спеки.

## 6. Открытые вопросы (для юридической консультации)

1. Достаточно ли взаимодействие по публичному HTTP API (loopback или TLS) квалифицируется как использование «at arm's length», исключающее статус combined work для Craft + внешний SiYuan? (вариант A — фундамент P1–P6)
2. Если бандлить немодифицированный SiYuan kernel в один установщик с Craft с процессной изоляцией и управлением жизненным циклом (managed) — это «mere aggregation» на одном носителе или combined work? От ответа зависит объём AGPL-публикации при варианте B.
3. Охват AGPL §13: распространяется ли source offer при нашем гипотетическом хостинге (модифицированного и немодифицированного) SiYuan для сетевых пользователей; что требуется, если хостинг появится после P7.
4. Условия и стоимость коммерческого/OEM-разрешения у правообладателя (Yunnan Liandi / siyuan-note): объём прав (распространение бинаря, модификации, товарный знак), цена, срок, процедура пересмотра; наличие прецедентов.
5. Товарный знак «SiYuan»: допустимость упоминания в UI Craft («Подключить SiYuan», «Управляемое ядро SiYuan») как номинативного; требования к дисклеймерам неаффилированности.
6. §6 anti-Tivoization против наших каналов дистрибуции (нотаризованные dmg, потенциально сторы): блокер ли это для варианта B на конкретных каналах, и как исключить канал не ломая релиз.
7. Авторское право на API-документацию SiYuan: достаточно ли clean-room переписывания типов по публичным докам (без копирования текстов); нужна ли оговорка об атрибуции.
8. Подтверждение, что публичность нашего форка `agisota/craft-agents-oss` сама по себе не создаёт AGPL-обязательств, пока в нём отсутствует код SiYuan (позиция варианта A).
9. Если потребуются изменения в самом kernel (например, новые API-точки): порядок контрибуции upstream (CLA/условия siyuan-note) и лицензионная обработка таких патчей при обоих вариантах (B/C).
10. Требуется ли формальное письменное заключение по варианту A до публичного релиза P2 (нативный Knowledge-раздел), или достаточно внутреннего анализа.
